## Platform data rules and implementation dependencies

- Define workspace activity as at least one recorded `source=workspace` submission in the selected UTC interval. Account lifecycle and onboarding status are current snapshots. Record timestamps for the interval and for data freshness. Distinguish zero activity, an unavailable data source, and an unknown metric.
- A recorded submission may be blocked or fail. A violation event is a matched policy event tied to a run. When reporting a violation rate, use evaluated terminal runs with at least one recorded violation as numerator and evaluated terminal runs as denominator. An empty denominator yields an unavailable rate. Keep evaluation runs and legacy imports out of ordinary adoption metrics.
- Use a dedicated platform response with an explicit field allowlist. Tenant prompt and violation serializers can return user names, emails, findings, notes or decrypted content, so they are unsuitable as platform response objects. Send only agreed company metadata, totals, derived flags and selected audit fields. Apply stable ordering and pagination on the server and cover legacy missing status/version according to established defaults.
- Scope details and joins to the selected company ID after server authorization. Existing tenant routes derive the company from the authenticated account. Preserve that shape even when the platform operator is inspecting another company. Verify a separate actor/target audit trail and protect the platform operator's home organization.
- Registration is the only public company creation flow observed. Owner-led provisioning needs a new operation joining company creation to an initial administrator invitation. It also needs send, retry, duplicate, and audit behavior because email delivery occurs separately from transactional changes. This is a product decision for pilots and sales-led onboarding.
